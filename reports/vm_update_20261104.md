백업은 각 VM에만 있으며 저장소 bundle, 환경파일·데이터·로그·보고서를 포함한 workspace archive, SQLite online backup 및 보존 파일 해시 목록을 포함한다. 백업 상위 디렉터리는 사용자 전용 0700이다. `.env.*`와 원본 DB·target 로그는 외부로 복사하거나 Git에 추가하지 않았다. 기존 target `logs/`도 유지했다. 모든 DB의 `PRAGMA quick_check`는 `ok`이며 최종 비교에서 기존 행이 모두 남아 있었다. 테스트로 생성된 새 세션/관찰 메타데이터는 기존 데이터에 추가될 수 있다.

각 서비스는 저장소 루트에서 다음 형식의 launcher를 별도 세션으로 실행했다. `ROLE`은 해당 VM의 target, worker, controller이며 target → worker → controller 순서로 시작했다.

```bash
.venv/bin/python -m common.service_config serve ROLE --env-file .env.ROLE
```

launcher의 서비스별 환경 검증·상속 설정 필터를 적용했다. 기존 환경파일은 최종 해시까지 동일하다. API 스타일·target 모드·정책·비밀번호·토큰을 변경하지 않았다. 새 부팅 자동 실행 서비스나 방화벽 규칙을 설치하지 않았다. 실행 로그와 PID는 각 VM의 `/home/ubuntu/securityaiagent/verification_tmp/deploy_20261104/`에 보관한다.

기존 읽기 전용 `securityai-update` 공유를 유지했다. 정제 결과 회수용 `securityai-results-20261104` 공유는 transient로 추가한 뒤 마운트 해제 및 VirtualBox 매핑 제거를 완료했다. 완료 시 세 VM에 기존 공유만 남았으며 NIC 설정도 유지됐다. 이는 방화벽·격리망 전체의 독립 보안 검증을 의미하지 않는다.
